プロジェクトに小さな機能を追加しました。より大きな変更には、堅牢なプロセスが必要です。GitHub Copilot app は組織の既存フローに沿って作業できます。このレッスンから数回にわたり、Issue から機能を作成し、コードと動作を確認して、プロジェクトへのマージを成功させるまでのエージェント主導の開発を行います。

> [!NOTE]
> 機能開発を続ける間は同じセッションを使います。通常はファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub Issue から新しいエージェント セッションを始めます。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで機能を実装します。
- コードをレビューします。
- ブラウザー Canvas で機能を手動検証します。

この機能の作業を続けながら、リポジトリの命令を更新し、quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリや発行元でゲームを絞り込む必要があります。バックログの Issue には機能が記されていますが、カテゴリの組み合わせ方など、コーディング前に合意が必要です。Plan モードで決めてから、Autopilot に範囲を定めた実装を任せます。

## 背景

AI コーディング エージェントを開発フローに加えても、基本は変わりません。一般的なフローは次のとおりです。

1. 必要な作業の詳細を記した Issue を開きます。
2. 実装計画を立てます。
3. コードを作成してレビューします。
4. テストを実行します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な手順はチームや組織によって異なりますが、多くは上記の流れを基にしています。

この方法を守ることで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビュー プロセスを通るようにできます。

## セッション モード

**セッション モード**は、エージェントの自律性を制御します。プロンプト欄の下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが協力します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが計画を作成します。実行前に計画を確認して承認します。
- **Autopilot**: エージェントが自律的にコードを書き、テストを実行し、入力を待たずに反復します。

まず Plan で計画を確認し、次に Autopilot で実装します。

## Issue からセッションを開始する

作業を始める前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリ フォルダーを選び、リポジトリ上部の **Issues** を選択します。
2. **Allow users to filter games by category and publisher** を開きます。テンプレートにある Issue を使うため、新しいものを作成する必要はありません。
3. **New session** を選び、更新済みの `main` を基にした **new working tree** を選択します。

   ![Issue ビューの New session ボタンを矢印で示した GitHub Copilot app の画面](../../../_images/app-new-session-from-issue.png)

4. Issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。通常のターミナルでは動作するのにセッションで見つからない場合は、アプリの PATH またはバージョン管理の設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで再インストールしないでください。

## 絞り込み機能を計画する

Issue から開始したため、Copilot は機能の要望をコンテキストとして持っています。次を送信し、コードを書く前にアプローチを確認します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと発行元による絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが含まれることを確認します。カテゴリを組み合わせる動作や、結果がない場合の動作など、不明な点を話し合います。

計画には、既存ツールによる lint、ユニットテスト、E2E テスト、型チェックを含めます。計画は絞り込み機能の実装とテストに絞り、品質ワークフロー完了後に PR を作成します。承認前に必要な変更を依頼し、後で検証できるよう Issue の URL と合意事項を控えます。

## Autopilot を明示的に承認する

計画に問題がなければ **Approve and implement this plan**、または使用中のバージョンで同等の選択肢を選びます。アクティブなモード表示が **Autopilot** であることを確認してください。Copilot は計画に沿って実装し、コード生成とテストを反復します。

> [!NOTE]
> 承認すると実装がすぐ始まる場合があるため、先に計画を確認してください。依存関係不足やポート競合が報告された場合は、チェック完了と判断する前に問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードをレビューし、テスト結果を確認します。

1. **Changes** を開き、絞り込み機能とテストを確認します。
2. 複数カテゴリや発行元の組み合わせも含め、結果を Issue と合意事項に照らし合わせます。既存のリポジトリ命令に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 失敗を解決し、影響するチェックを再実行してから実装を承認します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカル サーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテスト対象であることを確認します。

## 新機能を確認する

ブラウザー Canvas でサイトを開き、絞り込み機能を試します。

1. Copilot に次のプロンプトを送信します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. アプリが起動し、Copilot app 内にブラウザー ウィンドウが表示されるまで待ちます。
3. カテゴリを選んで結果を確認し、フィルターを解除してから発行元を選び、結果を確認します。
4. カテゴリと発行元を組み合わせ、Issue と計画に照らし合わせます。複数カテゴリに対応する場合は、合意した動作を確認します。
5. 結果がない組み合わせで空の状態を確認し、フィルターを解除またはリセットして一覧が戻ることを確認します。
6. 次のプロンプトで、このセッションで起動した開発サーバーを停止します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンに向けてセッションを保持する

まだ絞り込み機能の PR を作成またはマージしないでください。レッスン 4 から 8 まで同じセッション、worktree、ブランチを使います。次はカスタム命令を適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。サーバーを停止した後、セッションをそのままにしておきます。
